# M6 — Prototype: "Anonymity Assessment Studio"

All CLAUDE.md rules apply. Build on branch `m6-prototype`.
Framework: EDPB Guidelines 02/2026 on Anonymisation (adopted 7 July 2026).
Build order: 6.0 → 6.1 → 6.2 → 6.3. 6.3 is a stretch goal.

## Core rule: the app is a RECIPIENT
The app must run with SECURE_DIR unset. It reads ONLY:
- outputs/*.json (profile, baseline_risk, release_stats_*, risk_eval, utility_eval, sweep, tradeoff_grid)
- outputs/releases/aggregate.parquet
It never imports safety.load_raw and never touches raw data. Add a test that
imports the app modules with SECURE_DIR unset and asserts they don't call load_raw.
Stack: Streamlit (ask me before adding it to requirements) + pandas. One file per
page under app/pages/. Entry point: `streamlit run app/Home.py`.

## 6.1 — Page 1: Assessment walkthrough (the presentation backbone)
A step-by-step view following EDPB Annex 1:
1. Describe the situation: data, storage (SECURE_DIR, Finland-hosted compute), what could help re-identification.
2. "Is it obviously not anonymous?" Raw: YES (msisdn/imsi/imei). Show the M1 field classification (with human overrides highlighted).
3. Transform steps as cards: each shows approach, parameters, rows affected, and the risk it addresses (from transform_log_*.json).
4. The three criteria: for each release (raw, record, aggregate), a table of criterion × {simplified, contextual}: measured number, worst-off individual, verdict (pass / fail / pass-with-residual-risk) with one-line reasoning.
5. Utility: the U1–U4 headline numbers and the coverage gap by radio type and province.
6. Residual risks: the register (tested / mitigated / untested).
Visual: before/after bars for baseline vs record vs aggregate on each attack.
No numbers typed by hand: everything is read from outputs JSON.

## 6.2 — Page 2: Trade-off explorer (human in the loop)
Precompute script: `python -m src.tradeoff` (this one DOES use raw data; it runs
offline, before the app, and writes only aggregate metrics).
Grid: k ∈ {5, 10, 20} × time_bucket ∈ {15, 30, 60} × area_mode ∈ {enb_tokenised, province}
× ε ∈ {0.5, 1, 2} (aggregate). For each config, in memory via build_release +
the M3/M4 functions: % rows/cells suppressed, coverage (% subscribers), A1 worst-off
and mean identification probability, A2 trajectory result, A3 homogeneity %, A5
differencing recovery %, A6 attacker accuracy (smaller sample is fine), U1
headline, U3 bottom-10 overlap, U4 count error. Write outputs/tradeoff_grid.json.
Time-box: if the full grid is too slow, drop time_bucket 30 and run A6 only for ε.

App page: sliders/selects for each parameter → shows risk panel (the three
criteria, traffic-light per criterion) and utility panel, plus a scatter of all
configs (x = utility, y = worst risk) with the current one highlighted and the
deployed config marked. Configs failing any criterion under the contextual
approach are labelled "not releasable" and the approve button is disabled.
"Approve release" asks for reviewer initials + a reason and appends to
outputs/release_decisions.jsonl (config, metrics snapshot, reviewer, reason,
timestamp). Show the decision log below.

## 6.3 — Page 3 (STRETCH): AI analyst and AI red team
Both modes: Mistral via safety.llm_gateway (logged), tool-calling loop, max 6 steps.
The only data tool is `query_aggregate(filters, group_by, metrics)`, which runs
pandas locally on aggregate.parquet and refuses any result cell with
n_subscribers < 10. No arbitrary code execution.

Analyst mode: answer Elina's questions ("Where is 5G video experience worst?")
with a short answer, the table used, and a caveat line (DP noise, suppressed cells,
means not supported for QoE metrics).

Red-team mode (EDPB paras 83, 92–93): the agent gets the release schema and an
attacker-knowledge TEMPLATE (e.g. "you know the target's province, radio type,
app category and the 15-minute window"), never real target values. It proposes a
re-identification strategy as a sequence of tool queries. The harness then runs
that strategy locally for 200 sampled real targets (evaluation index in memory
only) and returns only the success rate to the agent and the UI. Show: the
agent's strategy, the success rate, and a comparison to the M3 hand-written attacks.
Log everything in llm_calls.jsonl.
