# M3 — Risk evaluation

All CLAUDE.md rules apply. Do Step 0 first (it changes what M3 measures),
then Steps 1–3. Step 4 (Anonymeter) is optional and time-boxed.

Threat model for every attack (state it in the outputs):
- **Recipient:** Elisa product team. No raw-data access, no hashing keys, no
  enb→token mapping, no auxiliary identity data (relative approach, EDPS v SRB).
- **Worst-case attacker (reported alongside):** knows some true (enb, time)
  points about a target, public enb→province geography, and in the aggregate
  differencing test, the true slice totals.
Every result is reported under both, labelled `realistic` and `worst_case`.

## Step 0 — Fix the DP claim before measuring it

1. **User-level sensitivity.** One subscriber can appear in several aggregate
   cells (different time buckets / app categories), so noise at scale 1/ε is
   not a user-level guarantee even for `n_subscribers`.
   - Measure cells-per-subscriber in the aggregate grouping (max, p99) and
     log it.
   - Add `max_cells_per_subscriber` to config/release.yaml (default: the p99
     value). Bound contributions: for subscribers above the cap, keep a
     seeded-random subset of their cells for the COUNT columns only.
   - Noise `n_subscribers` at scale = max_cells_per_subscriber / ε.
   - **Drop `n_rows` from the release** (not needed for analysis, and costly
     to protect).
   - Log the counting bias introduced by the cap (share of subscriber-cell
     pairs dropped).
2. **Noisy-threshold suppression.** Decide primary suppression on the NOISY
   count (noisy n_subscribers < aggregate_min_subscribers_per_cell), so the
   set of published cells is also covered by the mechanism. Secondary
   suppression stays as is.
3. **Scope of the guarantee.** QoE medians/p10/p90 and volume sums are NOT
   covered by DP; they are protected by the ≥10 threshold, winsorising and
   top-coding. Write this explicitly into release_stats.json `dp_scope` and
   docs/transformations.md.
4. **Mode-suffixed outputs.** Write transform_log_{mode}.json,
   release_stats_{mode}.json and docs/transformations_{mode}.md so running
   one mode can never overwrite another.
5. Re-run the ε sweep, `--mode all`, pytest and the leak guard.

## Step 1 — Evaluation harness: src/evaluate.py

- Refactor anonymise so `build_release(df, mode, cfg)` returns
  `(release_df, eval_index)`. `eval_index` maps release rows to subscriber keys
  **in memory only** for evaluation; it is never written, logged or returned
  from a CLI.
- CLI: `python -m src.evaluate` builds releases in memory from raw, runs all

- Seed 42 everywhere. Sample sizes configurable in `config/evaluate.yaml`.

## Step 2 — Attacks

For each attack record: id, name, Article 29 criterion (singling_out /
linkability / inference), attacker knowledge, baseline (raw) result, result per
release mode, and a one-line interpretation.

**A1 Row uniqueness (singling out).** Re-run baseline R1 on the record release
using its QI [time_bucket, area, radio_access_type, application_category]:
% rows in groups of size 1, % in groups < k (distinct subscribers), and
expected identification probability = mean over rows of 1/(distinct
subscribers in group). Compare with raw baseline QI set D.

**A2 Trajectory attack (linkability).** Attacker knows p ∈ {1,2,3,4} true
(enb, time_start) points for a target (sample 1000 subscribers with ≥ p points).
Map points to release coordinates: `worst_case` = attacker knows enb→area
mapping; `realistic` = province only.
- Record release: rows are unlinkable, so report, per known point, the number of
  distinct subscribers in the matching group and the probability of picking
  the target's row.
- Session release (if built): intersect session_ids present at all p points;
  report % with exactly one candidate.
- Raw baseline: the existing R2 numbers.

**A3 Homogeneity (inference, l-diversity).** Per record-release QI group,
sensitive attributes: tethering flag (tethering_data_GB_dl_sum > 0),
heavy-user flag (data_GB_sum > raw p95), video flag (im_video_GB_sum > 0).
Report % of groups where all members share the same value, the share of
subscribers in such groups, and the distinct l per attribute (min, median).
Flag groups homogeneous on a rare value (e.g. all tethering) separately: those
are the real leaks.

**A4 Outliers (singling out).** In the record release: % of rows at each
top-code cap; for heavy-user rows, the distinct subscribers sharing their
(QI, rounded volume) combination. Report how many heavy users remain in
groups < k when volume is added to the QI.

**A5 Differencing on aggregates (singling out).** `worst_case`: attacker knows
the true n_subscribers total per (time_bucket, province) slice. Attempt to
recover each suppressed cell as total − Σ published noisy cells. Report the
% of suppressed cells recovered within ±2 subscribers, with and without
secondary suppression, and at each ε in the sweep (and ε=none).

**A6 Membership inference on aggregates (inference).** Sample 200 subscribers.
For each target, build neighbouring releases with and without them (reuse the
full pipeline so suppression is included). Over 200 noise seeds, the attacker
sees one noisy release and guesses in/out with a likelihood-ratio test on the
target's cells. Report attacker accuracy (50% = random guessing) and advantage
at each ε and at ε=none. Also report the theoretical bound
e^ε/(1+e^ε) next to it. Time-box: use a smaller sample if it runs > 10 minutes.

## Step 3 — Report: docs/risk_assessment.md (generated, deterministic)

1. Threat model (recipient and worst-case attacker, as above).
2. Before/after headline table: rows = attacks, columns = raw baseline,
   record release, aggregate release (ε=1), session release if built.
3. One section per attack: method, attacker knowledge, result, interpretation.
4. Residual risks: every item from the CLAUDE.md list, each marked
   `tested (Ax)` / `mitigated by design` / `untested — why`.
5. What the DP guarantee does and does not cover (from Step 0).
6. Wording rule: never "anonymous" as an absolute; use "reduces measured risk
   to X under threat model Y".
